# エージェントアーキテクチャと実験計画

2026-07-09 の設計議論で確定した、プロジェクト全体の背骨。[学習によるルール獲得ループ.md](学習によるルール獲得ループ.md)（2026-07-08）の後継・具体化にあたる。以後の「積む/積まない」「学習するか手書きか」の議論は、本文書の枠組みの中の座標指定として行う。

## 1. 確定事項（背骨）

1. ルールベースによる行動空間の圧縮は維持する（確定済み方針）。
2. 意思決定は3層に分離する（§2）。**確定ルールは聖域**であり、学習は一切触れない。
3. 学習の対象は2箇所のみ — (a) 確定ルールが決めきれない候補の順位付け（選好スコア）、(b) 確定でないルールの前提（見えない情報の推測 = belief）。
4. 学習は**模倣で初期化 → RL で仕上げ**の2段構え（§4。逆順にしない）。
5. 部品の採否は事前議論でなく実験で決める。評価は3審級の漏斗（§5）に従う。

## 2. 決定の3層構造

```
候補手（合法手すべて）
   │
   ① 確定ルール（人間が書く・学習不可侵）
   │    リーサル確定 → 実行 / 次ターン負け筋 → カット / 禁じ手 → 除外
   │
   ▼ ①で決まらない場合のみ
   ② 選好スコア（学習対象）
   │    value = Σ_r θ_r · φ_r(s, a, z)
   │    述語 φ = 人間が書く。強度 θ = 学習で決める
   ▼
選択（決定的 argmax。確率化 T>0 は最後にラダー A/B で検証するだけ）
```

実装上は「バンド（辞書式の段）＋バンド内スコア」に対応する。現行実装（`agents/_base/policy_base.py`）は両者を**1個のスカラの桁**で多重化している（LETHAL_BAND=10^6、ハードマスク −10^5 前後、ソフト選好 ±10^4、タイブレーク ±1）。学習を入れる前にこの分離が必要（§6）。

なぜ聖域か：学習器が生スカラを動かすと、ソフト選好の重みがハードマスクの桁を侵食する事故が構造上ありうる。バンドを跨げない設計にすれば「マスクの誤りは学習では直らない」問題を①に封じ込め、安全性の検証対象を①だけに限定できる。

## 3. 搭載部品表

| # | 部品 | 何をするか | 今（ルールベース） | 学習でやる場合 | 教師信号 / 報酬 | 実行時間 |
|---|---|---|---|---|---|---|
| ① | 確定ルール | リーサル実行・負け筋カット・禁じ手の除外 | 実装済み | **学習しない（聖域）** | — | ≈0 |
| ② | 選好スコア | ①で決まらない候補の順位付け | 手書きの点数（7体分） | 点数の重みを最適化：模倣 → RL | 上位者の選択ラベル → 勝敗 | ≈0 |
| ③ | 見えない情報の推測 | 相手手札（ボス保持）・サイド落ちの推定 | カウンティングで大半可能（一部未実装） | カウントで説明できない残差だけ | **間接ラベルのみ**（エピソードは部分観測のみ格納・相手手札は None。後で公開されたカードからの遡及ラベル or カウンティング検証） | ≈0 |
| ④ | 局面評価 V(s) | 「この盤面どっちが有利か」を数値化 | なし | 回帰 / TD | 勝敗（自己対戦・エピソード） | ms |
| ⑤ | 1手読み | 有力候補を実際に1手進めて④で評価 | なし（0手読み argmax） | ④とセットで初めて意味を持つ | — | **秒/手 ← 時間制約の主戦場** |
| ⑥ | 相手デッキ判別 | 相手のアーキタイプ特定 → ②③の入力 | 場のカードとの照合（R-20） | ベイズ事後で足りる可能性大、学習不要かも | 相手デッキはエピソードで全公開（step1 action） | ≈0 |
| ⑦ | 出力の確率化 | 決定的でなく確率的に打つか | 決定的（argmax） | 基本不要。最後にラダー A/B で確認だけ | — | 0 |

RL 標準用語との対応：② = 方策のパラメータ、③⑥ = POMDP の状態推定（belief）、④ = 価値関数、⑤ = 遷移既知（シミュレータ所持）を活かしたモデルベース計画。

実行時間 600 秒プールを実質消費するのは⑤のみ。③⑥は numpy でほぼタダ。**部品採否の希少資源は実行時間ではなく評価スループット**（§5）。

議論で刈り済み（実験しない）：遷移モデルの学習（API 既知）／マスクなし end-to-end 方策（①②の圧縮は確定事項）／エピソード間の相手個体適応（obs に相手 identity が無い）。

## 4. 学習の2段構え（模倣 → RL）

### 段1：模倣（初期化＋計測器）

- 上位プレイヤーのエピソードは、各決定点が「候補集合＋実際に選んだ手」という **1手1ラベル**のデータ。softmax 分類（条件付きロジット。複数選択は Plackett-Luce）で θ を推定する。
- これは divergence mining の損失関数化そのもの。対戦生成が不要で、密で、低分散。
- 役割は2つ：RL の初期値（cold start 回避）と、上位者との乖離の計測器。**模倣は最終目的ではない**。

### 段2：RL（上位者の天井を超える）

- 報酬 = 勝敗。環境 = gauntlet（メタシェア加重の固定相手プール）。**自己対戦ではなく「推定された場」への最適応答**——ラダーは静的な集団なので均衡探索は不要。ローカルと実ラダーのズレはプールのデッキ構成（`research/meta/` の場推定）で埋める。
- 手法：θ が数十個のうちは CMA-ES / CEM（ブラックボックス最適化）。スコアラを NN 化したら方策勾配系へ切替。
- 実行環境：ユーザー所有サーバー（対戦生成の計算はここに寄せる）。
- 制約：1試合1ビット・評価ノイズ ±10pt@40試合 → 1点評価に80試合以上。プール過適合は holdout 相手で監視（§5）。

順番を逆にしない理由：報酬の疎さとノイズにより、ゼロからの RL は計算を初歩的着手の学習に溶かす。AlphaGo と同じ SL→RL 構成。

## 5. 実験プロトコル

### 3審級の漏斗

| 審級 | 物差し | コスト | ノイズ | 用途 |
|---|---|---|---|---|
| L0 | shadow 一致率・divergence 率・held-out の選択一致精度 | 秒〜分、**対戦不要** | ほぼ無 | リファクタ回帰検知、θ 候補の大量ふるい |
| L1 | gauntlet 制圧度（シェア加重勝率） | 80試合（スクリーニング）/ 320試合（確定） | ±7pt / ±3.5pt | 部品の採否判定 |
| L2 | 実ラダー A/B | アクティブ2枠・日5提出・600から登り直し → **週2〜3本が上限** | 大 | 唯一の真の目的関数 |

### 規律

- **昇格基準**：L0 pass → L1 スクリーニング（80試合）で正の差 → L1 確定（320試合）で **+7pt 以上**（ノイズの2倍）→ L2。加えて **holdout 相手**（gauntlet プールから意図的に外した 2〜3 デッキ）への非劣化を必須とする（プール過適合ヘッジ。ローカル評価は実ラダーを予測しないという ptcg-abc の教訓への防御）。
- **kill 基準**：L1 スクリーニングで差なし〜劣化 → 棄却し台帳に理由付き記録。time-box（目安3日）で L1 に到達しない部品 → 棚上げ。
- **交絡禁止**：現ベスト構成に1部品ずつ足して比較（貪欲前向き選択）。単体無価値のペア（④+⑤）は1部品として扱う。
- **分散削減**：cg エンジンにシード固定 API が無いため gauntlet での paired comparison（共通乱数）は不可（2026-07-09 調査）。gauntlet のノイズは試合数で吸収する。なお shadow 比較（同一 obs 列を両者に問い合わせ）は構造的にペアード済みで、挙動一致の検証にはこちらを使う。スループット実測 336 games/min（Windows開発機、EXP-001）により 320 試合の確定評価も約12分で回るため、試合数での吸収は現実的。
- **再現性**：オフライン計測は常に T=0（決定的）。
- **台帳**：`research/experiments/` に1実験1行（構成・L1 スコア±CI・判定・日付）。PROJECT_DIARY（時系列）と違い構成で引ける。戦略レポート部門（締切 2026-09-13）の実験セクションの原稿を兼ねる。
- **最初の計測タスク**：gauntlet のスループット実測（1試合何秒か）。これが週次の実験予算、ひいては 8/16 までに審査できる部品数の上限を決める。

## 6. 実装の縫い目（リファクタ指針）

1. **band / value / features 分離**：`score_option` の返り値を（バンド、バンド内スコア、述語発火記録、reason）に形式化。`choose()` のソートキーを `(band, value, -index)` へ。バンド操作（リーサル昇格・マスク）は人間管理、学習が触るのは value のみ。
2. **update_belief() 一本化**：`choose()` 冒頭の判定4行（matchup / phase / lethal / threats）を belief 更新として1関数に集約。`detect_matchup` のベイズ事後化、`judge_loss_threats` の boss_assumed → P(ボス∈手札) 化の差し替え点になる。
3. **実装＝ロギング**：features の発火記録がそのまま模倣学習の計画行列になる設計にする。訓練専用のコードパスは作らない（train/serve skew の排除）。
4. **θ の置き場**：`agents/<deck>/theta.json`。コード＝述語（R-xx、docs/planning 管理）、データ＝強度、の分離。
5. **移行の安全ゲート**：挙動を変えないリファクタとして実施し、`scripts/ab_battle.py --shadow` で新旧一致100%を確認してから切替。7体の資産は無傷で持ち越す。

## 7. ロードマップ（エージェント締切 2026-08-16）

- **Phase 1**：縫い目リファクタ（§6、shadow-safe）＋ gauntlet スループット実測 ＋ 実験台帳新設
- **Phase 2**：模倣パイプライン（θ 推定・L0 メトリクス整備）
- **Phase 3**：カウンティング一式（サイド落ち・アーキタイプのベイズ事後・ボス belief）→ ②の入力を拡張
- **Phase 4**：RL 仕上げ（サーバーで CMA-ES on gauntlet）
- **Phase 5**（間に合えば）：V(s) ＋ トリガーターン限定の1手読み

Phase 2 以降の各部品は §5 の漏斗を通し、採否はデータが決める。Phase 1 だけは全部の土台なので漏斗の外（挙動不変が合格条件）。
