# エージェント学習プロセス — ルール成熟 → BC → 模倣正則化つき PPO

2026-07-17 制定。エージェントを実装資産として成熟させる**正典パイプライン**。
関連文書: [エージェントアーキテクチャと実験計画.md](エージェントアーキテクチャと実験計画.md)（評価漏斗の正典）/
[学習によるルール獲得ループ.md](学習によるルール獲得ループ.md)（設計思想の原典）/
[評価方法.md](../planning/評価方法.md)（L0〜L4 の定義）。

## 0. 全体像

```
Phase R  ルール成熟（Windows）      φ を書く。ゲート A/B/C を満たすまで
   ↓
Phase D  教師データ抽出（Windows）  ルール確定後に必ず再抽出（候補集合が変わるため）
   ↓
Phase B  BC 事前学習（Windows）     残差 MLP を教師あり学習。holdout 一致率で検証
   ↓
Phase P  PPO 仕上げ（サーバー）     模倣正則化つき PPO（勝利項 = 主、模倣項 = 錨）
   ↓
Phase E  評価・採否（両方）         gauntlet L2 漏斗 → L4 実ラダー。LEDGER に記録
```

**設計原理**（なぜこの形か）:

1. **ルール = ネットの行動空間**。学習は正帯候補の並べ替えしかできない。教師の選択が
   候補外（負帯・13位以下）にある決定は、どんな学習でも到達不能 —
   **マスクの誤りは学習では直らない**（ルール獲得ループ §4）。だから前段でルールを成熟させる。
2. **プール自己対戦のみの RL はプールに過適合**し（EXP-009 の V 葉、CEM の教訓）、
   **模倣単独は学習が不安定でラダーでも負ける**（EXP-002 の −18pt）。
   → 目的関数を混合する: PPO の勾配に教師決定の CE 勾配を λ 加重で足す
   （DAPG / AlphaStar 型。train_ppo.py `--bc-data`、2026-07-17 実装）。
3. **ルール変更は学習資産を無効化する**（候補集合・reason・ルールスコアが変わる →
   npz 再抽出 + BC + PPO の再学習が必要）。学習開始後のルール追加は「不可」ではなく
   「1デッキ = 再学習1回ぶんのコスト」。だからルールは前段で大規模に成熟させ、
   以後は成果が再学習コストを上回るときだけ触る。
4. **コストは資産数に対して線形**（指数ではない）。相手は凍結プールからのサンプリング
   なのでプールサイズは 1 iteration のコストに影響せず、模倣項は既存 npz への
   教師あり損失でほぼタダ。リーグ学習（学習中の自分をプールに足す）はしない（正典 §7.2）。

## 1. Phase R — ルール成熟

**目的**: 学習ループに入れるデッキの行動空間（候補集合）から構造誤りを除く。

### 終了ゲート（時間でなく計測で決める）

| ゲート | 基準 | 計測方法 |
|---|---|---|
| **A: 構造被覆** | 教師行動の候補外率 ≤ **3〜5%**（被覆率 95%+） | `extract_bc_dataset.py --audit-jsonl`（下記） |
| **B: 収穫逓減** | ルール更新2回連続で L2 **+2pt 未満** | gauntlet 80→320 漏斗（P-12: 更新毎に再計測） |
| **C: プール側** | シェア上位 ~80% の相手アーキタイプのルールが破綻していない | 各デッキの check_agent + gauntlet 異常値の目視 |

### Gate A の計測（= 監査モード。2026-07-17 追加）

```powershell
$env:PYTHONIOENCODING='utf-8'
uv run python training/extract_bc_dataset.py `
    --episodes downloads/episodes/2026-07-13,downloads/episodes/2026-07-15 `
    --agent agents/alakazam_rb --match-deck decks/fleet/alakazam_top_0710.csv `
    --min-overlap 55 --min-score 1180 `
    --out build/rule_audit/<日付>/alakazam.npz `
    --audit-jsonl build/rule_audit/<日付>/alakazam.jsonl
```

末尾の `AUDIT` 行が機械可読サマリ。JSONL の中身:

- `kind=outside`: ネット対象決定なのに教師の選択が候補外。`human_band=negative` は
  「ルールが禁じた手を教師が選んだ」= 負帯化ルールの誤り疑い。`positive` は 13位切り捨て。
- `kind=narrow_mismatch`: 正帯<2 の一本道でルールと教師が不一致 = マスク過剰の疑い。
- `human_reason` でクラスタリングすると「次に書くべきルール」のリストになる。

**監査ダンプ → ルール化の規律**は divergence mining と同じ（EXP-013/021 の教訓）:
調整日/検証日を分ける（P-10）・両日で同方向のクラスタのみルール化・凍結プールで A/B・
ミラー除外（`--exclude` 自アーキ）・80戦1組で kill しない。

### Gate A と divergence mining の分担

- 監査ダンプ（候補**外**）= **φ の構造誤り**。学習で直らない。Phase R で潰す。
- divergence（候補**内**の並べ替え不一致）= 学習レイヤの領分。Phase B/P に委ねる
  （EXP-021: 相手モデル依存のさじ加減はルール直写し不可、学習適地）。

## 2. Phase D — 教師データ抽出

ルール確定後に**必ず再抽出**（PN_VERSION / 候補集合が変わるため。古い npz は
バージョンガードが弾く）。日毎に1ファイル:

```powershell

    --episodes downloads/episodes/<day> `

```

## 3. Phase B — BC 事前学習（Windows・数分）

```powershell
uv run python training/train_bc.py `
    --data "data/imitation/<deck>_bc/*.npz" `
    --eval-days <holdout日> --out models/bc_<deck>_vN.npz
```

- 残差型（epoch 0 = ルール完全一致）。**直接デプロイ禁止**（EXP-002）。
- ゲート: holdout 一致率がルール基準を明確に上回ること（実績: alakazam 50.3→60.4%、
  marnie 44.6→67.0%）。上回らない場合は教師データ量かルール側の問題 → Phase R へ戻る。

## 4. Phase P — 模倣正則化つき PPO（サーバー・数時間/デッキ）

```bash
docker compose run --rm ptcg uv run python training/train_ppo.py \
    --agent agents/<deck>_rb --deck decks/fleet/<deck>.csv \
    --field research/meta/<最新>_field.csv \
    --exclude <holdout3種（自アーキも学習プール外なら追加）> \
    --resume models/bc_<deck>_vN.npz \
    --bc-data "data/imitation/<deck>_bc/*.npz" --bc-eval-days <holdout日> \
    --bc-coef 0.3 --bc-coef-final 0.05 \
    --iters 60 --games-per-iter 256 --workers <物理コア-1> \
    --out build/ppo_bcmix/<deck>
```

- **λ（--bc-coef）は序盤強く終盤弱く**（線形減衰）。勝利項が主、模倣項は
  「プールで勝てる範囲で LB 挙動から離れるな」という錨。
- **監視**: history.csv の `bc_holdout`（iter 毎の holdout 一致率 = L0 連続計測）。
  これが学習中に大きく落ちる = プール過適合の開始。λ を上げるか iter を絞る。
  `win_rate` と `bc_holdout` の両方が本音の計器（学習中勝率はサンプリング方策の参考値）。
- デプロイ候補は **ema.npz**（EXP-006 winner's curse 対策）。
- 既存 history.csv がある --out へ追記するとヘッダ不整合（07-17 に列追加）。新しい出力先を使う。

## 5. Phase E — 評価・採否

1. **L2 スクリーニング**: `gauntlet --net build/ppo_bcmix/<deck>/ema.npz`、
   ミラー除外 80戦/枠（±7pt）。差なし〜劣化 → kill、LEDGER 1行。
2. **L2 確定**: 160〜320戦/枠（±3.5pt）。**+7pt 以上** + **holdout 3種非劣化**で昇格。
3. **L4**: zip 作成（`--extra ema.npz=policy_net.npz`）→ validate_episode 合格 →
   スカウト枠で実ラダー泳がせ 2〜3日。
4. すべて LEDGER に EXP-NNN で記録（試合数明記 = P-03）。

プール制圧度は参考値。**採否ゲートは L0（一致率）と L4（実ラダー）**（P-13、ユーザー指示 2026-07-15）。

## 6. バージョン規律（2026-07-17 の事故から）

**事故**: EXP-024 で `meta_tables.ARCHETYPES` に rocket を追加した際、value_model の
アーキタイプ one-hot が動的参照（`sorted(mt.ARCHETYPES.keys())`）だったため特徴次元が
82→84 に黙って伸び、**既存の全 policy_net / value_v3 / BC npz が沈黙縮退**していた
（ネットは例外を握って ルールにフォールバック = 気づけない）。同日修正:
one-hot 語彙を v3 時点の 11 アーキで**凍結リスト化**（value_model.ARCH_LIST）。

規律:

- 特徴量・候補ゲート・語彙に影響する変更は **FEATURE_VERSION / PN_VERSION を必ず加算**。
  加算 = 全 npz 資産の再生成を宣言する行為。コストを払う価値があるときだけやる。
- 新アーキタイプの追加は one-hot 凍結リストに**入れない**（unknown 枠に落ちる。許容誤差）。
  次回の全艦隊再学習時に v4 として一括拡張する。
- `sync_base.py --check` を変更後に必ず実行（_base とエージェント側コピーの一致）。
- 抽出・学習ツールはバージョン不一致で fail-fast する（黙って続行しない）。
  サイレント縮退を疑ったら check_agent の `net_used` / DIAG を見る。
