# ルール抽出（オープン実装より）

作成: 2026-07-06。出典は `research/external/`（ptcg-abc、公開Notebook 15本。詳細は `research/external/kaggle_notebooks/SURVEY.md`）。

ここは「エージェントに敷くルール」の確認場所。議論で追加・格上げ・棄却したら随時更新する。

## 強度の定義

ルールごとに強度を決める（ハードマスク一律でもソフト一律でもない）。

- 【ハード】違反手を候補から除外する。または一択を即返す。
- 【ソフト】スコアで強く優先/抑制するが、他の要因で覆り得る。
- 【タイブレーク】同点時の順序付けのみ。
- 【プロセス】エージェント本体ではなく開発手順のルール。

昇格条件: ソフト→ハードは「上位プレイヤーのエピソードで反例が(ほぼ)無い」ことを確認してから。

## 1. 安全性・時間管理（全部ハード）

- **R-01 例外=敗北。`agent()` 全体を try/except で包み、失敗時は先頭 minCount 個を返す**【ハード】— 提出後の検証エピソードは自分ミラーなので、例外1つで提出が Error 死する。（strong-start v10、ptcg-abc BasePolicy）
- **R-02 返却は常に minCount〜maxCount にクランプ、インデックス重複禁止**【ハード】（全実装共通）
- **R-03 ベンチ0体で手札に出せるたねが無い状況を作らない。Ultra Ball 等はベンチ0なら強制使用**（ドンク=即死回避）【ハード】（Archaludon）
- **R-25 `def agent` は main.py の「最後に定義される callable」にする**【ハード】—（2026-07-07 追加、実提出failで学習）Kaggle のローダー（kaggle_environments `get_last_callable`）はファイル内の**最後の callable** をエージェントとして採用し、引数も `co_argcount` に切り詰めて呼ぶ。`def agent` の後に関数・クラス・callable 代入を書くと別物が呼ばれ、検証エピソードが INVALID で即死する。ガード: build_submission の静的検査 + check_agent のローダー忠実検査 + **提出前に `scripts/validate_episode.py`（kaggle_environments 経由のミラー1戦 = Kaggle の Validation Episode の忠実再現）を必ず通す**。ローカルの cg 直叩き評価ではこの層のバグは見えない。
- **R-23 時間はプール制。「1手1秒」ではない**【ハード（事実+運用則）】— 環境定義（cabt.json）は `actTimeout: 0` + `remainingOverageTime: 600`。つまり1手ごとの上限はなく、**1試合・1プレイヤーあたり合計600秒**のプールを全意思決定で分け合う（使い切ると負け）。実エピソードの実測（2026-06-30、6試合）では意思決定は**片側40〜110手/試合** → 平均5秒/手以上使える計算。運用則: (a) 通常手はルールで即決（<10ms）、(b) 探索はトリガー条件を満たす手番だけ1〜1.5秒程度、(c) `obs['remainingOverageTime']` を毎手監視し、残量閾値（例: 120秒）を切ったら探索を無効化してルールのみに縮退。

## 2. ターン運びの構造

- **R-04 スコア帯=ターン内の行動順序。特性 > たね展開 > グッズ > 進化 > エネ付け > サポート > にげる > ワザ**【ソフト（構造）】— ワザが最下位なのは弱いからではなく「ターンを終わらせる行動」だから。公式サンプル4種とその派生（LB940/950）全てこの骨格。（kiyotah 公式サンプル）
- **R-05 攻撃計画（AttackPlan）を MAIN の頭で立てる: 攻撃者×ワザ×対象の全列挙で最良計画を決め、以後の全判断（ボス対象・エネ付け先・にげる・入れ替え）が計画を参照する**【ソフト（構造）】— 公式 Mega Lucario が原典。強い公開実装は全部この派生。
- **R-06 ターン頭でフラグをリセットし（`pre_turn != state.turn`）、使用済み特性を turn-scoped に記録する**【ハード（実装規約）】（5位Alakazam）

## 3. リーサルと詰め

- **R-07 この番で勝てるなら勝ち切る。ターゲット選択は3段優先: (1)残りサイドを取り切れるKO → (2)KO可能な中でサイド最多 → (3)倒せないならアクティブ削り**【ハード】— 一般ストラテジー.md の「勝てるときは勝ち切る」の実装形。（5位Alakazam）
  - **探索による厳密化（実現可能性は確認済み）**: リーサル確認は「ゲーム木の全展開」ではなく**自ターン内の手順列挙**（相手の応手なし、END/ワザ宣言で打ち切り）なので浅くて済む。Search API（`search_begin/search_step/search_release`、エンジン内蔵・C++でms/step級）を使い、multiply-agent は候補6手×ビーム幅3×4手先を**1.5秒予算**で回してラダー実戦投入済み（LB940）。1300+ Starmie は「勝てそうなターンだけ探索でリーサル検証→見つけた勝ち筋を再生」。時間は R-23 のプール制なので、トリガー式なら余裕で収まる。
  - トリガー条件の例: 「AttackPlan の最大打点+盤面のばら撒き/ボス込みで相手の残りサイドを取り切れる可能性がある」時のみ探索起動。
- **R-08 次ターンの負け筋を切る: 「相手の手札にボスの指令がある」前提の最悪ケースで被リーサル判定する**【ハード（辞書式フォールバック付き）】— 判定は可視情報＋明示的な最悪ケース仮定で行う（不完全情報の確率的補完はしない）。
  - 判定式: 自分の**全盤面**の各ポケモン P について、`相手最大打点(マッチアップ別テーブル、可変打点は floor/ceiling 推定) ≥ P の残HP` かつ「P を取られると負け（サイド計算 or 盤面崩壊）」なら、その手はロス手。**ボス想定により露出集合がアクティブだけでなく全ベンチに拡大**するのが肝。
  - 強度の運用（辞書式）: (1) 最悪ケースで負けない手を最優先 → (2) 全手が最悪ケースで負けるなら可視情報のみの判定に緩和 → (3) それでも全滅なら least-bad。ハードマスクだが手詰まりでフリーズしない。
  - 緩和条件: 相手トラッシュ（可視）のボス枚数が、アーキタイプ既知の採用枚数（detect_matchup + エピソード分析のコンセンサスリスト）に達したらボス想定を解除。サポート回収カードを積むアーキタイプは解除しない。
  - 探索でやる場合も同じ仮定を注入できる: Search API は `search_begin(obs, opponent_hand=…)` で相手手札を決定化できるため、**ボスを相手手札に置いた決定化**で相手ターンを1手読める。（公式RL/MCTSサンプルにシグネチャ記載）
  - 参考: Archaludon は対アラカザムで「相手手札枚数+盤面ドロー源から打点天井を計算、自分がKOするなら KO後の残りベンチで再計算」まで実装。（Archaludon 75%WR）
- **R-09 サイドペース管理: 自分サイド残2〜3で megaEx（3枚取られ）を前に出さない・攻撃を抑制**【ソフト】（公式Lucario、multiply）

## 4. 資源規律

- **R-10 エネルギー過剰付与の禁止: ワザの実コストから「もう払える」を判定し、追加付与を禁止。自己スケール技（エネ枚数×ダメージ）のみ例外**【ハード】— ptcg-abc で複数デッキにわたり再発した最多バグ。カード毎のハードコードではなくコストから導出する。（ptcg-abc BasePolicy）
- **R-11 山札切れガード: `safe_draws = 山札残 − 自サイド枚数 − 1` を超えるドロー消費を禁止。カード毎に消費枚数で閾値（Poffin<2, Hilda<2, …）。ただしこの番で勝ち切るなら解除**【ハード（解除条件付き）】— 一般ストラテジー.md の「圧縮は積極的に」への公開実装側の答えは「圧縮は善、ただしこの不等式は守る」。（5位Alakazam、strong-start は LOW_DECK=8 でドロー系封印）
- **R-12 ドロー特性・サポートの温存: KO や必須セットアップに必要な時だけ使う**【ソフト】— Dudunsparce/Fezandipiti を無条件で回すと山札とリソースが枯れる。（5位Alakazam）
- **R-13 DISCARD は勝ち筋ライン（メインアタッカー・進化パーツ・キーサポート）をハード保護し、余剰基本エネ・同名重複から捨てる**【ハード（保護リスト）+ソフト（順序）】（ptcg-abc、公式Abomasnow）
- **R-14 ベンチは1枠空けておく（テック・後続用）**【ソフト】（5位Alakazam: bench_free≤1 で -5000）

## 5. ターゲット評価

- **R-15 スプレッド/スナイプは相手の低HPエンジン駒（ドロー要員・進化元）を優先。倒せない高HP壁に撒かない**【ソフト】— ptcg-abc がラダー1位のプレイと比較して 27%→99% 一致まで直した箇所。multiply も Snover+950/Riolu+800（進化前を狩る）。
- **R-16 ボス司令の多段ロジック: リーサル最優先 → アクティブKOで足りるなら温存 → ベンチKO候補をサイド価値で選択 → 攻め手が無ければ「ボススタール」（にげ・技コスト大でエネ0のベンチを引きずり出して時間を稼ぐ）**【ソフト】（Archaludon）
- **R-17 相手の前ターンのワザを logs から追跡し、攻撃不可状態（Mega Brave 直後等）を突く/維持する**【ソフト】（Archaludon）

## 6. 情報推定（ルールの入力を作る層）

- **R-18 サイド落ち推定（PrizeTracker）: デッキリスト − 全可視ゾーン = サイド集合。解決中カード `obs.select.effect` を引き忘れない。曖昧なら unknown を返す — 誤推定は無推定より有害**【ハード（保守性の原則）】— サーチ・探索が「実現不可能な勝ち筋」を掴むのを防ぐ。実装は 1300 Starmie 公開版がドロップイン可能。公式 Dragapult サンプルにも serial ベースの簡易版あり。
- **R-19 ログから相手の ACE SPEC 使用を検出し、自分の対応カードの価値を切り替える**【ソフト】（5位Alakazam）
- **R-20 マッチアップ検出 `detect_matchup()`: 相手の場のカードID集合からアーキタイプを判定し、以後の分岐キーにする**【ハード（実装規約）】（Archaludon、strong-start の Crustle 検出）

## 7. 先攻・マリガン

- **R-21 先攻/後攻はデッキ固有。上位ピロットのデータから読む。勘で決めない**【ハード（デッキ毎に一択）】— Dragapult は後攻、Mega Starmie は先攻（1位 keidroid が27戦全部先攻）。（ptcg-abc）
- **R-22 マリガン: 常にマックス引く（2026-07-07 ユーザー決定）**【ハード・全デッキ】— BasePolicy の TAKE_MULLIGAN=True を標準とする。参考記録: 公開実装には NO 派も存在（Archaludon 参照実装・keidroid は NO、Alakazam 5位は YES）。ユーザー方針としてカード資源のマックス取得を優先。反証データ（上位ピロットの divergence で NO が明確に優位と出た場合）が出たら再議論。

- **R-24 ベンチは1枠空けておく（テック・後続用）。ただしベンチ0は最優先で解消（R-03）**【ソフト】— 5位Alakazam（bench_free≤1 で -5000）と自作マリィの2デッキで採用（2026-07-06 昇格）。R-14 を一般化して置換。

## 8. デッキ特化ルールの「型」

デッキ毎ルールは自由記述ではなく、以下の型に流し込む（型自体は全デッキ共通）。

1. **基礎スコア + `apply_overrides()` の2層**: 汎用スコアを出した後、マッチアップ別の上書き差分を一括適用。保守しやすく、上書きだけレビューすればよい。（Archaludon）
2. **打点計画モデル**: 可変打点デッキは「打点の源」を明示的にモデル化（例: 手札純増 min/max → Powerful Hand 上限。5位Alakazam の `estimate_hand_increase()`）。
3. **配分列挙**: ダメカンばら撒き系は DFS で「倒し切れる部分集合」を全列挙し、サイド獲得数で最良配分を選ぶ。（公式 Dragapult の Phantom Dive）
4. **閾値の実測チューニング**: 回復・温存などの閾値は勘でなくグリッドサーチ（Archaludon の回復閾値 Lucario=270 は 200..280 を10刻みで実測）。
5. **テックカードの出場ゲート**: 相手盤面の特定カード検出時のみ出す（Psyduck↔Duskull 等）。（5位Alakazam）

## 9. 開発プロセスのメタルール

- **P-01 賢そうなスコアリング追加は必ず A/B してから採用** — strong-start はベンチ設置/ディスカード/ダメカン配分のスコア追加「だけ」を入れたミラーで 70-30 で負けた。
- **P-02 スコア変更は divergence データ（上位ピロットとの不一致集計）で検証。勘で上げない** — ptcg-abc は EVOLVE スコアを勘で上げて2提出を無駄にした。
- **P-03 ローカル評価（cabt含む）は回帰検知の物差し。実ラダーが唯一の審判。40戦は±10ptブレる→結論は80戦以上**（ptcg-abc）
- **P-04 スコア関数は `(score, reason)` を返し、全採択理由を文字列で追えるようにする**（Archaludon）
- **P-05 共通ロジックは共有基盤（BasePolicy型）に集約し、デッキ固有判断は abstractmethod で実装漏れを防ぐ**（ptcg-abc）
- **P-06 デッキ+エージェントは棄却後も捨てない — 評価用の対戦相手プール・学習フェーズの相手方策資産になる**（ptcg-abc は棄却デッキを cabt 対戦相手として運用、任意デッキリストを相手化する GenericPolicy も保有）。当プロジェクトの置き場: `experiments/frozen_agents/`
- **P-07 挙動保存リファクタは shadow diff（全手番一致率100%）で検証する**（2026-07-06 追加）— 旧エージェントで対戦を進行しつつ全手番で新エージェントにも問い合わせ、選択の一致率を測る（`scripts/ab_battle.py --shadow`）。決定的で不一致箇所が特定でき、勝率A/B（80戦で±11%）より遥かに強い。BasePolicy 移行はこれで合格させた（2,411手一致）。
- **P-08 一人回しの「サブゴール到達ターン」は10試合では結論に使えない**（2026-07-06 追加）— 初手運（エースバーン不発→経路B等）で平均4.2↔8.0が普通にブレる。到達率と合わせて傾向のみ見る。回帰判定は shadow diff か80戦A/Bで。
- **P-09 プールだけで調整したルールは【暫定】**（2026-07-08 追加）— 相手が全部自作ピロットの評価（プールA/B・ガントレット）だけで採用したルールは「自作の癖に勝つルール」の疑いが残る。人間アンカー（ホールドアウト日の divergence 一致率が非悪化）か実ラダーで検証されるまで確定にしない。判定規則と非悪化の閾値（±3pt/5pt）は `評価方法.md`。
- **P-10 調整に使った日のエピソードで検証しない（時間ホールドアウト）**（2026-07-08 追加）— divergence 調整の train/test を日で分割する。デッキ設計md の divergence 節に「調整日 / 検証日」を明記。検証日は原則調整日より後（Daily Episodes の公開は翌日 00:08 UTC 頃。未公開の間は調整日と異なる直近日で代用し、公開後に再計測）。
- **P-11 ピロットスタイル3種（tuned/generic/frozen）の勝率ブレを採用時の感度チェックに使う**（2026-07-08 追加）— `gauntlet.py --styles` で同一相手デッキのピロットを差し替え、スタイル間で勝率が±15pt超ブレるマッチアップは「特定ピロットの癖に勝っている」疑い。その勝率を根拠にしたルールは【暫定】扱い。frozen は `experiments/frozen_agents/`（P-06 の資産）から。
