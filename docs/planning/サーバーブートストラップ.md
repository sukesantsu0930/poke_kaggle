# サーバーブートストラップ（gs83 / Docker）

学習ループ（gauntlet・模倣データ抽出・θ最適化）を自宅サーバーで回すための手順。
対象: gs83（Ubuntu 24.04, i7-7700K 4C/8T, 62GB RAM, TITAN X Pascal 12GB, driver 535 = CUDA 12.2）。
**ホストは Docker のみ・Python 無し**。ホストに必要なのは git / docker（+compose）/ ssh だけ。

## 1. コードの取得（git）

```bash
git clone git@github.com:sukesantsu0930/poke_kaggle.git
cd poke_kaggle
```

## 2. gitignore 資産の転送（git には載せない）

コード＝git、データ＝転送、の分離。以下は `.gitignore` 対象なので clone に含まれない：

| 資産 | 場所 | サイズ | 転送方法 |
|---|---|---|---|
| 対戦エンジン | `submission/cg/`（libcg.so = Linux x86-64 同梱） | 小 | 必須。scp |
| エピソード | `downloads/episodes/<date>/` | 約1GB/日 | scp か、サーバー側で直接DL（下記） |
| リーダーボード | `downloads/leaderboard/` | 小 | scp |
| Kaggle トークン | `.kaggle/` | - | サーバー側DLする場合のみ |

Windows 側から（PowerShell、OpenSSH 標準の scp）:

```powershell
scp -r submission/cg suketomo@gs83:~/poke_kaggle/submission/
scp -r downloads/episodes suketomo@gs83:~/poke_kaggle/downloads/
scp -r downloads/leaderboard suketomo@gs83:~/poke_kaggle/downloads/
```

エピソードをサーバー側で直接落とす場合は `.kaggle/` を転送のうえ、コンテナ内で
`scripts/download_episode_sample.py` を使う（日次の追加取得はこちらが楽）。

## 3. Docker イメージのビルドと初回セットアップ

```bash
docker compose build
```

**初回の注意**: イメージには `/workspace/.venv` が焼き込まれているが、compose が
リポジトリを `/workspace` にマウントするため**焼き込み venv は隠れる**。初回に
マウント先へ venv を作り直す：

```bash
docker compose run --rm ptcg uv sync
```

以後 `docker compose run --rm ptcg <cmd>` がそのまま使える（`.venv` はホスト側
リポジトリ直下に永続化される）。

GPU（Phase 4 の NN 化まで不要）: compose は `gpus: all` を要求するため、
nvidia-container-toolkit 未導入なら `docker-compose.yml` の `gpus:`/`deploy:` 節を
一時コメントアウトして CPU で使う。GPU を使う段になったら
`uv run python scripts/docker_gpu_check.py` で torch から見えるか確認
（Pascal sm_61 + driver 535 と base image CUDA 12.4 の互換はこの時点で実測）。

## 4. スモークテスト（コンテナ内、各1行）

```bash
docker compose run --rm ptcg bash -lc '
uv run python -c "import sys; sys.path.insert(0,\"submission\"); from cg import api; print(len(api.all_card_data()))" &&
uv run python scripts/sync_base.py --check &&
uv run python scripts/check_agent.py --agent agents/archaludon_rb --deck decks/candidates/archaludon_cityleague.csv --games 5 &&
uv run python scripts/gauntlet.py --agent agents/dragapult_rb --deck decks/candidates/2026-06-30_top5/popular_4_dragapult.csv --games 8 &&
uv run python scripts/replay_divergence.py --episodes downloads/episodes/2026-07-06 --agent agents/marnie_munkidori_rb --archetype-cards 648,112 --min-score 900 --max-games 1
'
```

合格基準（上から順に）: カード数が表示される（libcg.so ロードOK）／ exit 0 ／
`OK all invariants pass` ／ 完走して `throughput:` 行が出る ／ 完走（episodes 転送OK）。

**gauntlet の throughput 実測値を `research/experiments/LEDGER.md` の EXP-001 に追記する**
（参考: Windows開発機 336 games/min。サーバーの週次実験予算の根拠になる）。

## 5. 学習ループの実行（Phase 2-4、コンテナ内）

```bash
# (1) 模倣データ抽出: 上位ピロット（LB1000+・自リスト重なり45枚+）の決定ログ → data/imitation/
uv run python training/extract_decisions.py                     # 全7デッキ×全日次

# (2) θ 適合（条件付きロジット）: held-out 一致率と θ 上位を確認して書き出し
uv run python training/fit_theta.py --deck marnie --out build/fit/marnie_theta.json

# (3) CEM 仕上げ: gauntlet 制圧度を直接最大化（時間のかかる本番運用はサーバー向き）
uv run python training/optimize_theta.py \
    --agent agents/marnie_munkidori_rb \
    --deck decks/candidates/2026-06-30_top5/winrate_2_marnie_grimmsnarl.csv \
    --init build/fit/marnie_theta.json --top-k 24 \
    --pop 12 --elite 3 --iters 30 --games 24 --out build/cem/marnie

# (4) 採用判定: L1 確定（320試合・+7pt・holdout相手）→ 合格なら theta.json をデッキdirへ
uv run python scripts/gauntlet.py --agent <θ入りコピー> --deck <csv> --games 320
cp build/cem/marnie/theta_best.json agents/marnie_munkidori_rb/theta.json  # 採用時のみ
```

聖域は実行時ガード（`_apply_theta` の band 凍結）が常時保証するため、
最適化がどんな θ を出しても確定ルール（リーサル・マスク）は壊れない。

## 6. 運用メモ

- cg はプロセスグローバル状態を持つため、並列化は**プロセス並列**で行う
  （8スレッドなら gauntlet を `--only` でアーキタイプ分割して複数プロセス起動）。
- 学習成果物は `models/`（gitignore、`models/README.md` のみ管理）へ。デッキ毎の
  θ は `agents/<deck>/theta.json`（提出 zip に自動同梱される）。
- Windows ↔ サーバーの同期はコードは git 経由、データ（新しいエピソード等）は
  scp / サーバー側DLで追加。**サーバーで作った学習成果を Windows に戻すのも scp**
  （git に載せるのは採用が確定した theta.json 等の小さいものだけ）。
